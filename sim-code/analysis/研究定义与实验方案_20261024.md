# 多机器人共享 VLM 的物理动作感知 KV 管理：研究定义与实验方案

日期：2026-10-24。本文整理研究问题、已有证据、算力与模型选择、实验设计和推进门槛。所有数字都标明来源：**实测**（来自 2026-10-22 RoboTHOR 预实验）、**离线回放**（基于实测块轨迹的模拟）、**推算**（按公式和标注的假设计算，开工前需实测校准）。

---

## 0. 一段话摘要

多台机器人共用一个 VLM 推理服务时，每台机器人的主 agent 和 subagent 会话会在机器人执行物理动作期间暂停，随后带着更长的历史回来。暂停会话的 KV 总量一旦超过 HBM 预算，vLLM 原生的 LRU 会遇到经典的循环访问问题：被淘汰的恰好是下一个要用的会话。损失也不是平缓增加，而是悬崖式的。单个请求暂停时如何保留 KV，已经有 InferCept、Continuum 等工作；工业界也已经提供保留提示接口（Dynamo、TensorRT-LLM）。尚未解决的是：**多个会话同时暂停、总量超过容量时，按什么顺序保留和恢复；以及物理动作"进行中可以观测进度"这一性质，能否让下次调用时间的预测足够准，从而决定淘汰顺序和恢复时机。** 本文用模拟器生成真实框架的调用图，加上真实机器人动作时长的标定和真实 vLLM 实测，分四道门槛检验这一问题。

### 1.2 机制支撑：推理服务已经开放保留提示，但没人决定提示怎么填

## 2. 相关工作与差异化

| 工作 | 解决了什么 | 尚未覆盖的部分 |
|---|---|---|
| InferCept（ICML 2024） | 单个请求暂停时，在保留、丢弃、换出三者中选择 | 暂停被当作黑盒；没有多会话超额订阅 |
| Continuum（arXiv 2511.02230，ICLR 2026，基于 vLLM） | 按预测的工具调用时长设置 TTL，把 KV 固定在 GPU；程序级 FCFS | TTL 逐请求独立设置，**所有 TTL 加起来超过容量时没有排序**；时长只在暂停开始时预测一次 |
| MORI；Adaptive KV Retention（arXiv 2608.30830） | 秒级工具暂停；分钟到小时级的人工审批暂停 | 暂停期间看不到进度 |
| KVFlow（NeurIPS 2025） | 按工作流图"还有几步轮到它"淘汰，并从 CPU 预取 | 按步数而不是连续时间；工作流图需事先已知 |
| Resident KV Claims（arXiv 2605.24259） | 未来复用的保留约定；容量不够时可以拒绝 | 作者明说只是约定，不是替换算法 |
| Leyline（arXiv 2606.01065） | 编辑上下文时保留基数树前缀 | 关注上下文编辑，不涉及淘汰顺序 |
| 经典缓存（LIRS、ARC 等） | 已知 LRU 在循环访问模式上表现很差 | 不知道 agent 会话结构和物理信号 |

**本课题可以站住的差异化（都需要实验证明）：**
1. **多会话超额订阅下的排序**：保留什么、先丢谁，而不只是"一个会话保留多久"。
2. **可观测进度的暂停**：剩余路径距离、操作阶段、VLA 动作块序号等信号，可以在动作进行中不断修正下次调用时间的预测。
3. **任务状态提供的无用块信号**：STOP、subagent 返回、重规划都会让一批块彻底失效。
4. **任务关键度加权**：STOP 核验等调用的延迟直接影响机器人是否停在正确位置。

## 3. 研究问题定义

### 3.1 问题陈述

> 不超过 8 台机器人共用一个 VLM 推理服务。每台机器人的主 agent 与 subagent 会话在执行物理动作期间暂停。当暂停会话的 KV 总量超过 HBM 预算时，推理服务应在每个决策时刻决定：保留哪些会话的哪段前缀；被淘汰的前缀何时、以何种方式（从 CPU 换入或重算）恢复到 HBM。目标是在 HBM 容量约束下，最小化机器人等待模型的总时间，并对 STOP 核验等关键调用的尾延迟加权。

### 3.2 决策时刻的输入与输出

决策时刻 t 包括：请求到达、一次推理结束、收到机器人状态更新。

**输入（运行时可得）：**
- 会话集合。每个会话有：所属机器人、角色（主 agent / subagent）、父子调用关系、状态（推理中 / 动作中 / 已结束）。
- 每个会话的物理进度信号：导航用剩余路径长度和速度，操作用 VLA 动作块序号、夹爪状态、所处阶段。
- `request_id` → KV 块 → 引用者的映射；每块位于 HBM、CPU 还是已丢失。
- GPU 队列、HBM 剩余空间、PCIe 链路占用。

**不可作为已知输入的：** 未来的调用时间、动作的真实结束时间、将来的新图像。这些只能估计。

**输出：**
- 每个前缀的动作：保留 / 换出到 CPU / 丢弃；
- 对已淘汰的前缀，决定恢复方式（换入或重算）和开始时间；
- 前台请求的优先级。

### 3.3 目标与约束

- **目标：** 最小化 Σ（机器人等待模型的时间 × 关键度权重），同时控制关键调用的 P95 首 token 时间。
- **硬约束：**
  - 驻留 KV 加正在推理的 KV 不超过 HBM 预算；
  - 前台请求优先，后台的恢复工作可以推迟、取消或拒绝；
  - 共享块只有在物理引用计数归零时才算真正释放，撤销一个会话的引用不等于块已腾空。
- **理论参照：** 如果事先知道每个会话的下次调用时间，问题退化为前缀树上的最优离线淘汰（Belady 类）。在线时只能从进度信号估计下次调用时间，因此预测误差直接决定策略能比 LRU 好多少。

### 3.4 agent 模式与 KV 访问类型的对应

从 KV 角度，与其按"多角色 / 主 agent 加 subagent / 单 agent"分类，不如按访问行为分类：

| KV 访问类型 | 典型来源 | 访问特征 | 关键信号 |
|---|---|---|---|
| A. 主循环会话 | 每台机器人的主 agent（VoLo、单 agent 循环） | 周期性回访，历史逐轮追加；多台机器人合起来呈**环形**访问 | 动作剩余时间 |
| B. 事件触发的 subagent | 目标核验、执行监控（EMERGE-Policy、本预实验的 target_review） | 回访间隔长且不规律；常处在关键路径上（STOP） | 触发条件、关键度 |
| C. 临时 subagent | 按子目标创建，返回后作废 | 返回后整段 KV 失效 | subagent 返回 / 子目标结束 |
| D. 并行扇出 | 多个角色同时处理同一观测（PARTNR 多 agent、多角色协作） | 共享同一份图像或观测前缀 | 引用计数 |

## 4. 已有证据（2026-10-22 预实验与 2026-10-24 离线回放）

### 4.1 实测：一个完整的冷回访链

- **配置：** Qwen3-VL-8B-Instruct，vLLM 0.30.0，单张 RTX 5090，`--gpu-memory-utilization 0.85`，KV 池 **3146 块 × 16 token = 50,336 token = 6.92 GiB**；8 条 RoboTHOR 长尾 ObjectNav 任务各当作一台机器人并行回放；图像 320×240。
- **规模：** 470 个请求（planner 435、target_review 35），不同的块共 3741 个。
- **冷回访链（四环齐全）：** GarbageCan 任务的 target_review 第 3 轮到第 4 轮：
  1. 同一分支确实回访，相隔约 16 秒；
  2. 新请求与旧请求有 32 个完全相同的连续块（512 token）；
  3. 这些块在旧请求结束时仍在 HBM，回访前因其他机器人 planner 的分配被全部淘汰；
  4. 回访时 `cached_tokens=0`，688 token 全部重算。

  详见 [KV逐块证据](robothor_multiround_20261022/KV逐块证据_20261022.md)。
- **局限：** 这条任务是事后挑出来的；路线由 oracle 生成；按仿真墙钟回放，约 0.25 秒一步；整体工作集只超出容量约 19%（3741 ÷ 3146 = 1.19）。

### 4.2 实测：淘汰对象中 94% 本来就无用

631 次淘汰中，**596 次（94%）淘汰的是之后再也不会被查找的块**；只有 35 块是之后还会用到的，其中 32 块就是上面那次冷回访。问题不在于容量绝对不够，而在于淘汰顺序：LRU 把较早释放、但仍会被用到的 subagent 块，排在了较新、但已经无用的块前面。

### 4.3 离线回放：不同容量下的淘汰策略

**复核说明（2026-10-24）：** 本节旧脚本的 `term_lru` 与 `phys` 用完整轨迹中的最后一次请求推断机器人结束，含未来信息；`phys` 只用调用间隔均值，并未读取物理进度。因此表内这两列只能作为探索性结果，不能作为在线策略收益。后续在线因果回放与物理预测检查请用 [实验准备说明](物理信号KV实验准备_20261024.md) 中的新脚本。

方法：用实测块哈希序列，固定请求内容，只改变 HBM 容量。命中按"连续驻留前缀"计算，与 vLLM 一致。不模拟时间反馈和正在执行请求占用的块。脚本：[kv_policy_trace_sim.py](../scripts/serving_study/kv_policy_trace_sim.py)。

表中数字是**超出首次必然缺失之后多出来的缺失块数**（必然缺失：planner 3136 块，subagent 302 块）；括号内是占 planner 全部查找块（95,345 块）的比例。

| 容量（块） | 工作集 ÷ 容量 | LRU（vLLM 原生） | 环形：先淘汰刚服务完的会话 | 间隔预测 + 任务结束信号 | 事先知道未来（参照） |
|---|---|---|---|---|---|
| 3146（实测值） | 1.19 | subagent 多缺 35 块 | 0 | 0 | 0 |
| 2600 | 1.44 | subagent 多缺 119 块 | 0 | 0 | 0 |
| 2200 | 1.70 | 813 | 704 | 218 | 68 |
| 1800 | 2.08 | 5,424（5.7%） | 3,951（4.1%） | 2,750（2.9%） | 1,507（1.6%） |
| 1400 | 2.67 | 16,047（16.8%） | 11,233（11.8%） | 8,095（8.5%） | 5,259（5.5%） |
| 1000 | 3.74 | **43,464（45.6%）** | 25,711（27.0%） | 18,867（19.8%） | 14,871（15.6%） |
| 700 | 5.34 | 70,035（73.5%） | 42,184（44.2%） | 36,191（38.0%） | 31,691（33.2%） |

各策略说明：
- **间隔预测：** 用每个会话调用间隔的滑动平均预测下次调用，**还没有使用真实的物理进度**。
- **事先知道未来：** 逐块的最优离线淘汰，同时间按"从尾部先淘汰"打破平局。它不是前缀缓存的严格最优，只作为参照。
- **校验：** 在实测容量 3146 块下，模拟中 LRU 让 subagent 多缺 35 块，与实测的 32 块相符。

**subagent 与 planner 的取舍（多出的 subagent 缺失块）：** 容量 1000 块时，LRU 627、环形 269、间隔预测 691、参照 611。间隔预测会优先淘汰调用间隔长的 subagent，而 subagent 恰好处在 STOP 关键路径上。

**单独加"任务结束信号"（LRU + 机器人结束后其块优先淘汰）：** 在 2600 和 3146 块时消除全部多余缺失；在 1000 块时几乎无效（43,333 对 43,464）。

### 4.4 由此得到的判断

1. **"环形而不是 LRU"在主循环上成立。** 多台机器人的主 agent 轮流调用，构成循环访问，正是 LRU 最差的情形：容量从 2200 块降到 1000 块，LRU 的多余缺失从约 1% 升到 46%。环形策略能挽回约 40%。
2. **但"环"只是特例。** 只有各机器人周期相同时，环形顺序才等于最优顺序。更一般的形式是按"预测的下次调用时间"淘汰；只用调用间隔预测就已明显好于环形，真实的动作进度预计还能更进一步。
3. **存在两种状态。** 压力小（工作集 ÷ 容量 < 约 1.5）时，关键是识别并丢掉无用块；压力大时，关键是按下次调用时间排序。
4. **必须按关键度加权。** 只看调用间隔，会把关键的 subagent 先淘汰。

## 5. 三个 insight 与可证伪条件

| 编号 | insight | 证伪条件（出现即放弃或改写） |
|---|---|---|
| I1 | 缓存压力取决于所有存活会话的上下文之和，而不是机器人数量。主循环形成循环访问，工作集超过容量后 LRU 呈悬崖式退化；压力较小时，损失主要来自无用块迟迟不被淘汰 | 在真实配置（真实框架、真实图像分辨率、不人为缩小显存）下，工作集 ÷ 容量始终小于 1；或 LRU 多出的重算量不到全部 prefill 的 5% |
| I2 | 物理动作是**可观测进度的暂停**：剩余时间的预测误差随动作推进而缩小。按预测下次调用时间排序，在超额订阅时优于 LRU、逐请求 TTL 和按步数淘汰 | 进度信号在需要做决策的时刻（淘汰或开始恢复时）没有让预测误差比"会话历史均值"明显更小 |
| I3 | 动作期间 GPU 大多空闲，从 CPU 换入比重算快一个数量级以上，所以"能否恢复"不是瓶颈，"何时恢复"才是：太早会挤掉下一个即将调用的会话，太晚机器人就要等；PCIe 带宽是多个会话共享的资源 | 不管何时开始恢复，机器人等待时间都差不多（说明恢复时机不重要）；或者链路不拥挤时，按需换入的延迟本身就可以忽略 |

## 6. 算力、模型与 HBM 能容纳多少上下文

### 6.1 每 token 的 KV 大小

公式：**每 token 的 KV = 2（K 和 V）× 层数 × KV 头数 × 头维度 × 每元素字节数**，BF16 时每元素 2 字节。

| 模型 | 文本主干：层数 / KV 头 / 头维度 | 每 token 的 KV（BF16） | 权重约（BF16） | 权重约（FP8） |
|---|---|---|---|---|
| Qwen3-VL-8B | 36 / 8 / 128 | **144 KiB** | 16.3 GiB | — |
| Qwen3-VL-32B | 64 / 8 / 128 | **256 KiB** | 62.2 GiB | 32.7 GiB |
| Qwen3-VL-30B-A3B（MoE） | 48 / 4 / 128 | **96 KiB** | 57.9 GiB | 30.4 GiB |

- 架构参数取自 Hugging Face `config.json`，开工前需复核（命令见附录）。
- 权重大小按参数量 × 字节数估算，FP8 版本多算 5% 余量。
- **8B 的数字已被实测交叉验证：** 3146 块 × 16 token × 144 KiB = 6.91 GiB，与 vLLM 报告的 6.92 GiB 一致。

### 6.2 HBM 中 KV 的预算

公式：**KV 预算 = gpu_memory_utilization × 显存 − 权重 − 非 KV 开销**。非 KV 开销包括激活峰值、视觉编码器的显存探测、CUDA graph 等。

- **校准：** 5090 显存 31.84 GiB × 0.85 − 16.3 − 6.92 ≈ **3.8 GiB**，这是 8B 模型在 `max-model-len 32768` 下的非 KV 开销。
- 32B 的非 KV 开销按 6 GiB 估计，30B-A3B 按 5 GiB 估计，都需开工时从 vLLM 启动日志实测。
- 除 5090 的 0.85 一行外，下表其余行都按 `gpu_memory_utilization 0.90` 计算。

### 6.3 每台机器人的上下文规模（三个负载档位）

| 档位 | 含义 | 每步 token | 每台机器人结束时的上下文 |
|---|---|---|---|
| S0 | 预实验：320×240、单相机，约 60 步 | 约 140（图像约 80 + 文本约 60）；实测 planner 中位数 3448、最大 8118 | 约 9.6k（planner 8.4k + subagent 1.2k） |
| S1 | 640×480、单相机，约 60 次调用 | 约 360（图像 20×15 = 300 + 文本约 60） | 约 24k |
| S2 | 640×480、三相机，历史截断到 32k | 约 960 | 约 39.5k |

- 图像 token 的算法：Qwen3-VL 每个视觉 token 对应 32×32 像素（patch 16 × 合并 2）。

### 6.5 平台选择及理由

选择原则：**不靠人为缩小显存，让真实配置自然覆盖"工作集 ÷ 容量"从小于 1 到大于 2 的区间**，同时设置一个问题应当消失的反例。

| 平台 | 模型 | 角色 | 理由 |
|---|---|---|---|
| **P1：1× RTX 5090** | Qwen3-VL-8B BF16 | 主平台（已具备） | 对应"每个场地一台边缘工作站服务不超过 8 台机器人"；已有探针和校准数据；S0 到 S2 的比值为 1.2–6.3，覆盖从压力较小到压力很大；PCIe 5.0 x16 可用来做 CPU 二级缓存实验 |
| **P2：1× H100 80GB（PCIe 5.0 主机链路）** | Qwen3-VL-32B FP8 | 主平台二 | 模型更大，更接近"机器人大脑"的质量需求；每 token 256 KiB；三档比值为 0.57 / 1.44 / 2.37，**刚好横跨悬崖前后**；数据中心级的现场服务器形态 |
| **P3：P2 硬件** | Qwen3-VL-8B BF16 | 反例 | 比值 0.21–0.85，问题应当消失。用来说明"在什么条件下不需要本方法"，让论文的结论有边界 |
| 备选 | L40S + 8B，或 H200 + 32B BF16 | 替换 P1 或 P2 | 按可用资源替换，比值范围相近 |

**不选统一内存平台（GH200、Jetson AGX Thor、DGX Spark）作为主平台：** 在这些平台上 CPU 与 GPU 共享内存，或通过 NVLink-C2C 连接（GH200 单向约 450 GB/s），"换出到 CPU"的代价接近于零，二级缓存问题基本不存在。可以在讨论部分说明。

### 6.6 换入与重算的成本

| 情形 | 会话 KV 大小 | 从 CPU 换入（有效 25 GB/s，PCIe 4 或拥挤的 PCIe 5） | 从 CPU 换入（有效 50 GB/s） | 重算（推算） |
|---|---|---|---|---|
| 8B，S0（9.6k token） | 1.32 GiB | 约 57 ms | 约 28 ms | 约 1.6 s |
| 8B，S1（24k） | 3.31 GiB | 约 142 ms | 约 71 ms | 约 4.0 s |
| 32B，S1（24k） | 5.89 GiB | 约 253 ms | 约 126 ms | 约 2.7–4.0 s |
| 32B，S2（39.5k） | 9.64 GiB | 约 414 ms | 约 207 ms | 约 4.4–6.6 s |

- 重算推算：每 token 约 2 × 参数量 FLOPs（8B 约 16 GFLOP，32B 约 66 GFLOP）；5090 按有效 100 TFLOPS，H100 FP8 按有效 400–600 TFLOPS。未计入注意力的平方项和视觉编码器重跑，因此是**下限**。
- 实际只需搬运被淘汰的那部分前缀，不一定是整个会话。

**由此得到三点：**
1. 换入比重算快 **20–30 倍**，"选换入还是选重算"不是主要问题。重算只在前缀很短、或链路极度拥挤时才可能更划算。
2. 但换入的绝对时间并不小：一个会话要 **几十到几百毫秒**，与一次推理的首 token 时间（预实验 planner 中位数约 220 ms）处在同一数量级。所以必须提前恢复，恢复时机就是问题本身。
3. 链路带宽是共享资源：8 台机器人在 S1 下每 2 秒各换入一次，需要约 13 GiB/s，相当于 PCIe 4 实际带宽的一半以上，恢复的先后顺序会直接影响等待时间。

## 7. 实验方案

### E0：主流框架的上下文管理方式（不需要 GPU，约 1 周）

- **目的：** 确认"可复用的长前缀"真实存在。如果不存在，后续实验都没有意义。
- **对象：** EMERGE-Policy、partnr-planner（PARTNR）、RAI、VoLo（如果代码已开放），以及本项目现有的 harness。
- **记录：**
  - 历史是只追加、滑动窗口截断，还是摘要压缩；
  - subagent 的上下文是否隔离、生命周期多长、返回后是否作废；
  - 每步调用次数、每次调用带几张图、图像分辨率；
  - 系统提示是否在不同角色之间共享。
- **产出：** 一张"框架 × 上下文策略"表，并据此修正 6.3 节的 S1、S2 档位。
- **通过条件：** 至少两个主流框架保留只追加的历史，或保留可复用的长前缀。否则课题改为"支持上下文编辑的 KV 管理"（参考 Leyline），不再沿当前方向推进。

### E1：用模拟器生成真实工作负载，测量工作集和悬崖（GPU 约 10 小时）

- **工作负载（与预实验挑选冷回访的任务组相互独立）：**

| 调用模式 | 模拟器 / 基准 | 框架 | 规模 |
|---|---|---|---|
| A 类主循环加 B 类核验（导航） | RoboTHOR、HM3D ObjectNav（Habitat） | 现有 planner 加 target_review | 每个模拟器 5 组 × 8 台机器人 |
| D 类多角色、多机器人 | Habitat 3.0 + PARTNR | partnr-planner | 5 组，每组 2–4 个 agent |
| C 类临时 subagent（操作） | LIBERO（EMERGE-Policy 使用的基准）；可选 RoboLab（Isaac Lab，120 个任务） | EMERGE-Policy | 5 组 × 8 个任务 |

- **方法：**
  1. 在 P1 上用真实 VLM 跑一遍，冻结回答，以保证调用图可以复现；
  2. 用块级探针（`install_vllm_cache_probe.py`）记录完整的块轨迹；
  3. 离线计算工作集，并用回放脚本把各平台换算成不同容量。
- **自变量：** 机器人数（2、4、8）× 负载档位（S0、S1、S2）× 平台与模型（P1、P2、P3）。
- **指标：**
  - 工作集 ÷ 容量随时间的变化；
  - LRU 多出的重算 token 占全部 prefill 的比例；
  - 淘汰对象中无用块的比例；
  - 冷回访率，按 A、B、C、D 四类分别统计。
- **通过条件（I1）：** 在 P1-S1 或 P2-S1 等真实配置下，峰值工作集 ÷ 容量大于 1.3，且 LRU 多出的重算超过全部 prefill 的 5%；P3 反例中，这一比例接近 0。

### E2：物理时间层与"下次调用时间"的可预测性（主要用 CPU，约 1–2 周）

- **为什么需要：** 模拟器按仿真墙钟回放，约 0.25 秒一步；真实机器人每步 1–5 秒。时间被压缩时，GPU 的忙闲比例和暂停长度都是错的。
- **时间模型：**
  - 导航：动作时长 = 路径长度 ÷ 底盘速度（0.3–1.0 m/s）+ 转向角 ÷ 角速度（30–90°/s）+ 噪声；进度信号是剩余路径长度。
  - 操作：用 DROID（真实 Franka 机械臂，带时间戳的轨迹）或 Open X-Embodiment 标定各类动作的时长分布；进度信号是 VLA 动作块序号、夹爪状态、所处阶段。
  - 失败与重试：按预实验和基准里的失败率注入。失败会让剩余时间突然延长，这正是只用历史均值预测会失效的场景。
- **比较三种下次调用时间预测器：**
  1. 只看最近一次使用时间（LRU 隐含的假设）；
  2. 会话历史均值或分位数（Continuum 的做法）；
  3. 用进度信号在线更新的剩余时间估计。
- **指标：** 在动作进行到 10%、30%、50%、70%、90% 时的绝对误差和排序准确率（任意两个会话谁先回访，判断是否正确）。
- **通过条件（I2，整个课题的生死实验）：** 在决策真正发生的时刻（淘汰时、提前换入的时刻），预测器 3 的排序准确率明显高于预测器 2。若不成立，就去掉"物理信号"这个卖点，课题退回到"调用结构加任务结束信号"。

### E3：策略对比（先离线回放，再在真实 vLLM 上跑子集；GPU 约 30 小时）

- **策略：** LRU（vLLM 原生）、逐请求 TTL（Continuum 式）、按步数淘汰（KVFlow 式）、环形、间隔预测、进度预测（本方法）、事先知道未来（参照）。
- **消融：** 分别去掉任务结束信号、进度信号、关键度权重、以及多会话联合排序（只保留逐会话 TTL）。
- **设置：** 在 P1、P2 上跑 E1 的负载；按 E2 的时间层，以真实节奏回放；每个配置 3 个随机种子。真实运行的量约为 7 种策略 × 3 个档位 × 2 种机器人数（4、8）× 3 个种子 × 2 个平台 ≈ 250 次，每次约 3 分钟。
- **指标：**
  - 重算 token 数；换入字节数和次数；
  - **机器人等待模型的时间**（主指标，直接关联任务完成时间）；
  - 关键调用（STOP 核验）的 P95 首 token 时间；
  - 全部请求的 P50、P95 延迟，用来确认没有损害其他机器人；
  - 后台恢复工作被取消或浪费的比例。
- **通过条件：** 在工作集 ÷ 容量大于 1.3 的配置下，本方法相对 vLLM 原生和 Continuum 显著降低机器人等待时间，且其他请求的 P95 不变差；在 P3 反例上不劣于 vLLM 原生。

### E4：CPU 二级缓存与恢复时机（GPU 约 8 小时）

- **微基准：** 在 P1、P2 上实测不同前缀长度下的换入时间和重算时间，画出两者的交叉点，并修正 6.6 节的推算。
- **恢复时机扫描：** 换入开始时间取"预测回访前 0、100、300、1000 ms，以及动作开始时立即换入"五档，分别测：
  - 恢复太早造成的额外淘汰（挤掉了其他会话）；
  - 恢复太晚造成的机器人等待。
- **链路竞争：** 8 台机器人、S1 档位，同时换入时的排队与先后顺序。
- **两类需求分开统计：** 正在推理的请求被抢占后的恢复，与已结束调用留下的前缀被后续调用复用。
- **通过条件（I3）：** 由进度触发、并检查 HBM 剩余空间的恢复方式，机器人等待时间低于"按需换入"和"动作一开始就预取"这两个极端，且额外淘汰可控。

### B. 主要公式

- 每 token 的 KV = 2 × 层数 × KV 头数 × 头维度 × 每元素字节数
- KV 预算 = util × 显存 − 权重 − 非 KV 开销
- 可容纳 token 数 = KV 预算 ÷ 每 token 的 KV
- 工作集 ÷ 容量 = Σ（各存活会话的上下文 token 数）÷ 可容纳 token 数
- 换入时间 ≈ 被淘汰前缀的 token 数 × 每 token 的 KV ÷ 有效链路带宽
- 重算时间 ≈ 被淘汰前缀的 token 数 × 2 × 参数量 ÷ 有效算力（下限）
