# 8 台机器人多轮核验：一次已完成前缀的完整冷回访链

日期：2026-10-22。**结论范围：构造并实测到一个存在性 case；不是负载普遍性、插件收益或工业 trace 的证明。**

## 最快的 case 构造

用冻结的 8 条 RoboTHOR 长尾 ObjectNav 图像轨迹，把每条 episode 视作一台独立机器人，按仿真程序墙钟间隔并行回放到同一张 RTX 5090 上的 Qwen3-VL-8B-Instruct/vLLM 0.30.0。每台机器人有一个主角色和一个事件触发的目标核验 subagent；核验角色保留自己的追加式多轮历史。主角色候选目标与新视角触发核验，终点再核验一次。用首次运行的回答冻结后续历史，避免模型输出变化改变调用图。模型使用原生 APC、约 6.92 GiB KV 池，无人为缩容。

此 case 选择了事先发现冷回访的 `FloorPlan_Train1_1_GarbageCan_65`，故属于**事后诊断案例**。第三次核验在 step 11，第四次在 step 53；二者之间约 16 秒，其余机器人与本机器人主角色持续请求服务。此次带只读观察器的复跑完成 470/470 条请求，无错误，第 4 轮仍冷启动。观察器记录 vLLM 实际多模态请求的块哈希、块 ID、查找、写入、释放与重分配驱逐；原始模型代码在实验后已恢复。

## 四环证据

| 必需环节 | 本次实测 |
|---|---|
| 同一分支确实回访 | `target_review` 第 3→4 轮，step 11→53；旧请求结束后 16,045 ms 才发起新请求。该 subagent 在本 episode 共 7 轮。 |
| 新请求有精确匹配的旧前缀 | 两次请求在 vLLM 实际 `request.block_hashes` 上有连续 **32 个完全相同块**；每块 16 token，即 512 token。第 3 轮提示 523 token，第 4 轮 688 token。多模态图像 extra hash 已进入 vLLM 块哈希，因此是实际缓存键的逐块匹配。 |
| 旧块曾在 HBM，后因分配离开 | 第 3 轮释放时，32 个匹配哈希均仍映射物理块；随后、回访前，32 个块全在 `BlockPool._maybe_evict_cached_block` 的重新分配路径被移除。18 个由另外两台机器人的 planner 请求触发，14 个由同一机器人的 planner 请求触发。首个匹配块在旧请求释放后约 10,593 ms 被移除。回访查找时 32 个均不驻留。 |
| 回访重算 | 第 4 轮 `cached_tokens=0`、`created_cache_tokens=688`，首 token 时间 **80.3 ms**。这证明发生重算；80.3 ms 是总首 token 时间，不能全部归因于 512 token 的缓存损失。 |

第 3 轮在查找时命中 368 token，又写入 144 token；恰好组成 32 个完整块的 512 token 前缀。第 4 轮之后的第 5 轮重新命中 704 token，说明该核验会话仍在正常追加历史，而不是每轮天然不可复用。470 次服务端查找均唯一对齐到相应客户端请求，驱逐事件所归属的分配请求也全部落在相应请求的客户端时间区间内。

先前未加观察器的固定输入对照中，相同第 4 轮请求在 4 台和 1 台运行下均命中 560/688 token；8 台两次均为 0/688。此对照支持并发压力解释，但调用时序、图像处理和探针开销不同，**不能把首 token 时间差当作插件可获得的加速量**。

## 可以与不可以声称的结论

这个 case 已满足“再次调用 → 精确旧前缀 → 物理块被容量分配驱逐 → 回访重算”的存在性标准。它属于**已结束调用的前缀回访**；不属于正在服务请求的抢占恢复。此前 8 台运行的运行中抢占计数为 0，本次证据不证明抢占需求。

它尚不证明：独立采样场景中冷回访的发生率、核验调用对真实闭环导航成功率的贡献、保留这些 KV 后对其他请求的净影响、任务状态策略优于通用缓存策略。当前导航路径来自 oracle，`STOP` 为影子决策，不是工业机器人轨迹。论文可用它作为 **mechanism/insight case**，不能用它单独支持工作负载代表性或插件收益。
